| 2026-09-06 | Mohit | Claude Code (Opus) | Add the live sensor seam: DeviceSensorSource emitting `Flow<MotionFrame>` from SensorManager | I set the requirement that the detector should not know whether the data comes from the phone sensors or a recorded trace. This means the same code used for the live demo is also used by the replay tests. The AI implemented the sensor pairing by keeping the latest accelerometer and gyroscope readings and emitting them on a 50 Hz tick, only when the accelerometer timestamp has advanced. This avoids reusing stale readings as if they were new data. It also used TYPE_ACCELEROMETER instead of TYPE_LINEAR_ACCELERATION, since the detector thresholds are based around gravity, and used SensorEvent.timestamp instead of the wall clock to avoid timing issues during a workout. It also found that CLAUDE.md referenced a com.repmate.data.model package that did not exist and corrected the package layout. |
| 2026-09-09 | Mohit | Claude Code (Opus) | Fix two detector defects: rep windows that never close, and a smoothing filter whose length depended on the device sample rate | Two issues were found when replaying the wider trace set. First, when a phone is left still after a set, its reading stays around 9.81, which is between lowThreshold (9.7) and highThreshold (10.15). This meant a rep window could stay open indefinitely, with 36.9 seconds of a stationary phone being counted as one squat. The fix was to check for this condition while the detector is running rather than only when the window closes. Second, the moving average used 25 samples, which meant the actual smoothing time changed depending on the device sample rate. It was 250 ms at 100 Hz, but 430 ms on the Samsung trace and 500 ms on the live 50 Hz stream. The filter was changed to use timestamps so that its behaviour follows the observed sample rate. This required changing minAmplitude from 0.75 to 0.94, and duration was no longer used as a separate guard because the 250 ms wobble could last 743 ms, which is longer than the shortest genuine rep at 615 ms. The trade-off is documented in the KDoc. Two outdated comments in the synthetic-trace test were also corrected. |
| 2026-09-09 | Mohit | Claude Code (Opus) | Support traces recorded in g, and add a fourth participant (iOS) as an out-of-sample check | The iOS Sensor Logger export records acceleration in multiples of gravity rather than the m/s² values used by the existing traces. Without explicitly handling the units, the existing thresholds around 9.81 would not work correctly. The AI added a units field to the .expect format instead of trying to guess the units from the data. Unknown units are rejected in the same way as unknown keys. It also identified that the iOS Accelerometer.csv could not be used because gravity had already been removed. The new fixture passed 10/10 using thresholds derived from the other three recordings. This also independently validated maxRepDurationMs, since removing that guard caused the trace to report 11 instead of 10 reps. However, it did not provide additional evidence for minAmplitude, because Lisa's reps were already well above the 0.94 threshold. |
| 2026-09-10 | Mohit | Claude Code (Opus) | Derive per-user thresholds from a five-rep calibration set | Across the four traces, the same exercise had a large difference in amplitude, so using one fixed minAmplitude would not work well for every user. The AI derived the four calibration guards from the first five reps and used the measured difference between the beginning and end of each set to calculate the safety margins. It also added checks for calibration data that is either inconsistent or outside a reasonable range. The calibration was tested by using reps 1–5 to create a profile and then detecting reps 6–10. All four traces achieved 5/5. However, this is still an in-sample validation because the default thresholds were developed using the same traces. It mainly shows that the calibration process does not break the existing detector. One limitation is still open: calibration does not solve the case where a user's movement is too weak for the Schmitt trigger itself to detect. |
