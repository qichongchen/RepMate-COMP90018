Context for Claude Code. Read this fully before writing or editing code. It defines the rules, the data contracts, and the conventions for this project. When something here conflicts with a request, follow this file and say so.

---

## What RepMate is

An Android app that turns a phone into a bodyweight-exercise form coach. Using only the accelerometer and gyroscope, it automatically counts reps (squats, push-ups, jumping jacks), scores each rep's movement quality, and shows a motion-replay graph explaining the score. It adds ghost duels and a leaderboard via Firebase. Phone-only: no wearable, no camera, no external hardware.

This is **signal-processing and state-machine engineering, not machine learning or "AI."** Keep it that way.

---

## Golden rules (do not break these)

1. **The engine is pure Kotlin.** Everything in `engine/` and `replay/` has **no Android imports** — no `android.*`, no `SensorManager`, no `Context`. It must run in plain JVM unit tests. Sensor reading lives only in `sensors/`.
2. **The engine consumes `Flow<MotionFrame>` and does not care where frames come from.** Live sensors and recorded JSON files both produce the same stream, so the code we demo is identical to the code we test. Never leak a sensor type into the engine.
3. **The data models below are frozen.** Do not rename or restructure `MotionFrame`, `RepEvent`, `RepScore`, or `WorkoutSession` without being asked — every workstream depends on them.
4. **Add KDoc to every public class and non-trivial function**, especially signal-processing logic. The authors are examined orally on this code; comments must explain *why*, not just *what*.
5. **Every detector and scorer has replay-based unit tests.** Record a trace once, assert forever.
6. **Never hardcode secrets.** API keys come from `local.properties` via `BuildConfig`; Firebase config comes from `google-services.json`. Use placeholders and tell the human what to provide.
7. **Degrade gracefully.** A missing sensor or a failed network call must never crash — emit a sensible default.

## Package structure

Under `app/src/main/java/`. **Packages that exist today** — import from these, they are what compiles:

```
com.repmate
├── engine          # Models.kt (the frozen data classes below), RepDetector,
│                   #   TraceLoader, SyntheticTrace                        (PURE Kotlin)
└── sensors         # SensorSource, DeviceSensorSource -> Flow<MotionFrame>
                    #   (the ONLY package allowed android.* imports)
```

Engine test-support code (`TraceLibrary`, `LabelledTrace`, `TraceExpectation`) lives in the
same `com.repmate.engine` package under `app/src/test/java/`, so it is not shipped in the APK.

The Compose scaffolding generated by Android Studio (`MainActivity`, `ui.theme`) sits under
`com.example.repmate`, which is also the module's `namespace`/`applicationId` — that is where
`R` and `BuildConfig` are generated. New RepMate code goes under `com.repmate`, not there.

**Planned packages** — not created yet, so do not import from them until they are:

```
com.repmate
├── data.local      # Room: entities, DAOs, database
├── data.repo       # repository interfaces
├── replay          # SessionReplayer  (PURE Kotlin)
├── cloud           # FirebaseRepo, leaderboard, ghost sharing, safety check-in
├── ui              # Compose screens, ViewModels, navigation
├── debug           # developer/replay-inspector mode (debug builds only)
└── di              # Hilt modules
```

Rule of thumb for placement: raw sensor access → `sensors/`; anything that reasons about reps or scores → `engine/`; anything that stores or syncs → `data.local/` or `cloud/`; anything on screen → `ui/`.

**The `sensors` / `engine` split is the load-bearing one.** `com.repmate.sensors` is the single
package permitted to touch `android.*` (`SensorManager`, `Sensor`, `Handler`). Everything in
`com.repmate.engine` stays pure Kotlin with no Android imports, which is what lets the detector
and its replay tests run on the JVM. `SensorSource` is the seam: it hands the engine a
`Flow<MotionFrame>` and the engine never learns whether the frames came from hardware or a
recorded trace. Putting an `android.*` import in `engine` breaks the test suite — that is the
rule this layout exists to enforce.

## Frozen data models

Treat these as the source of truth. Do not change field names.

They live in **`com.repmate.engine`** — `app/src/main/java/com/repmate/engine/Models.kt`,
alongside `RepDetector` and `TraceLoader`. So the import is `com.repmate.engine.MotionFrame`.
There is no `com.repmate.data.model` package; an earlier draft of this file named one, and code
written against it will not compile.

```kotlin
package com.repmate.engine

data class MotionFrame(
    val tMillis: Long,
    val ax: Float, val ay: Float, val az: Float,   // accelerometer
    val gx: Float, val gy: Float, val gz: Float     // gyroscope
)

enum class ExerciseType { SQUAT, PUSHUP, JUMPING_JACK }
enum class RepPhase { IDLE, DESCENDING, BOTTOM, ASCENDING, TOP }

data class RepEvent(
    val index: Int,
    val startMs: Long,
    val endMs: Long,
    val amplitude: Float
)

data class RepScore(
    val repIndex: Int,
    val score: Float,          // 0–10
    val tempoSeconds: Float,
    val rangePercent: Int,
    val pauseSeconds: Float,
    val reasons: List<String>  // e.g. "good depth", "slightly rushed"
)

data class WorkoutSession(
    val id: String,
    val exercise: ExerciseType,
    val startedAt: Long,
    val reps: List<RepScore>,
    val frames: List<MotionFrame>? = null   // kept for replay/dev mode
)
```

## How rep detection works (domain primer)

So you generate correct logic, not guesses:

1. Sample accelerometer + gyroscope at ~50 Hz; pair into `MotionFrame`s.
2. Low-pass filter the signal (moving average or exponential) to remove jitter.
3. A per-exercise **state machine** tracks the movement cycle (squat: IDLE → DESCENDING → BOTTOM → ASCENDING → back to IDLE). One full cycle = one rep.
4. Reject false positives with guards: minimum amplitude, minimum duration, correct sequence order, cooldown, and a stable finish. A fidget or half-rep must not count.
5. Score the rep from its window: range of motion (amplitude), tempo (duration), pause (dwell), consistency (variance) → `RepScore` with plain-language reasons.

Thresholds are tuned from recorded traces via the replayer — that's why recording and replay are core, not optional.

**Important scope note:** the app judges **movement quality** (depth, tempo, control, completeness), **not body posture** (knees, back). A single phone can't see joint geometry. Never write code or comments that claim posture correctness.

## Conventions

- One class per file; follow the package structure above.
- Immutable data models; expose state as `StateFlow`; Compose is stateless and observes it.
- **No business logic in Compose UI** — screens observe, ViewModels decide, the engine computes.
- All I/O (sensors, network, DB) off the main thread (`Dispatchers.IO`); never block the UI thread.
- Kotlin conventions; assume ktlint (formatting) + Detekt (static analysis). Functions ~40 lines max (guideline).
- Conventional commit messages if you commit, e.g. `feat(engine): add squat detector`.

---

## Testing requirements

- Determinism: the same seed/trace + same input always produces the same reps and scores.
- `RepDetector`: correct counts on recorded traces; a "fidget" trace → 0 reps.
- `FormScorer`: sensible scores on synthetic good/bad reps.
- Use bundled recorded session JSONs as test fixtures.
- The engine must be testable off-device (pure JVM) — this is why it has no Android imports.

---

## Scope guardrails — do NOT build these (they are v2 / out of scope)

- Camera or pose estimation of any kind (no CameraX, no ML Kit, no MediaPipe).
- Machine-learning classification (no TensorFlow Lite). The MVP is rule-based.
- Runtime calls to any external LLM/AI to judge reps or form.
- Heart-rate / wearable integration, fatigue detection, exercise auto-classification, left/right symmetry.
- Pull-ups or any exercise requiring the phone to be off-body.

The v1 exercise set is exactly: squat, push-up, jumping jack. If a request implies any of the above, flag it as out of scope and confirm before proceeding.

- Ask for **one unit at a time** (one class, one screen, one DAO) — not the whole app.

- If a design choice is open, pick the simplest robust option and leave a short `// NOTE:` explaining it.
- After a change, briefly say what you did and whether the human must do anything (e.g. add a key, run on a device).
- The human runs the app on a real phone and reports back logs/behaviour — you can't test haptics, sensors, or feel on your own.
